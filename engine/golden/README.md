# Golden corpus

Plans whose native TaskJuggler outputs the browser engine must reproduce exactly
(`docs/phases/phase-0.md`, section 6). `manifest.json` lists them; `expected/<id>.json`
holds each plan's recorded output.

The manifest holds 39 plans: the five upstream examples (read in place from
`engine/tj/examples/`), the PoC sample, the 22 synthetic plans below, the 8 bridge fixtures
(see "Bridge fixtures" further down), and the three Gantt plans (see "Gantt fixtures" below).

Every golden holds result schema 2 (`GoldenFile.schemaVersion`, `GOLDEN_SCHEMA_VERSION` in
`lib.mjs`): the phase-0 fields plus the bridge v2 fields of `docs/phases/phase-2.md` 6.1, decided
in `docs/decisions/0007-engine-data-and-derived-display-data.md` (see "Fields worth knowing").
A golden of another schema fails the parity test with one line that says to re-record it.

Cross-check limits: tj3's task report (`cross-check.tji`) checks task dates, dependencies (the
other task and which ends each edge joins) and every `complete` the plan sets, but TaskJuggler
has no report column for dependency gaps, the scheduling direction, the project's working time
or `dailyworkinghours` (details in "What a run does", step 4). Only parity and the fixtures
cover those four.

## Recording native outputs

`record-native.mjs` produces `expected/<id>.json` and `native-timings.json` from the real
TaskJuggler 3.8.4 in `engine/tj/` on native Ruby. It is a developer script: CI never runs
Ruby, `tj3` or Bundler.

### Setup

- Ruby 3.4.x, the version ruby.wasm runs. Any other version needs `--allow-ruby`, and the
  version is recorded in every golden as `native.ruby`.
- The recorder's gems, pinned in `Gemfile.lock`:
  `BUNDLE_GEMFILE=engine/golden/Gemfile bundle install`. They are `term-ansicolor` (with
  `tins`, `sync`, `bigdecimal`), plus `drb` and `base64`, which Ruby 3.4 no longer ships as
  default gems but TaskJuggler requires on its scheduling path. `mail`, `webrick` and
  `prawn` are never loaded by scheduling or by the cross-check report. Native runs use
  these real gems, not `engine/stubs/`.

### Commands

| Command | What it does |
| --- | --- |
| `node engine/golden/record-native.mjs` (`npm run golden:record`) | Record every manifest plan |
| `... --only <id>` (repeatable) | Record only these plans; other goldens and timings stay |
| `... --verify` (`npm run golden:verify`) | Re-run natively and fail on any difference from the committed files |
| `... --allow-ruby` | Accept a Ruby other than 3.4.x |

With npm, pass options after `--`, for example `npm run golden:record -- --allow-ruby`.

The script refuses to run when `engine/tj` is not the tree pinned in `engine/tj.pin.json`
(modified, untracked and ignored files all count), when Ruby is not 3.4.x, when native Ruby
does not sort ties stably (see below) or disagrees with the time-zone edge-case table (see
"Time-zone edge cases"), or when `engine/bridge/` or `engine/golden/plans/` have uncommitted changes (goldens
must come from committed inputs). Commit plan and bridge
changes first, then record, then commit `expected/` and `native-timings.json`.

**Stable sorting.** TaskJuggler sorts with ties in places (for example the candidates of
`select minallocated` are compared by criticalness only), so its result depends on how
Ruby's `Array#sort` orders equal elements. Natively that is the C library's `qsort_r`.
glibc's is a merge sort in every released version, so equal elements keep their order (its
only unstable path is a fallback when the merge buffer cannot be allocated, far beyond plan
sizes). macOS and musl (Alpine) are not stable. ruby.wasm has no `qsort_r` and uses Ruby's
own unstable quicksort, so the browser bridge loads `engine/bridge/wasm/tj_wasm_sort.rb`,
which makes `Array#sort`, `Array#sort!` and `Enumerable#sort` stable. Native recording
stays unmodified TaskJuggler and never loads that patch: record on a glibc-based Linux such
as Debian or Ubuntu (not Alpine or macOS).

Before every record or verify run the script runs a tie probe twice natively: plain, where
every order must keep ties in input order, and with `tj_wasm_sort.rb` loaded, where every
order must be identical to the plain run. It refuses to run if either fails, so the patch is
checked against native Ruby each time. Before the patch, `syn-15-allocate-select` picked a
different resource in ruby.wasm.

The goldens committed now were recorded with Ruby 3.3.6 and `--allow-ruby`, most recently
for result schema 2 (phase-2 T2). They are provisional until the user re-records them with
Ruby 3.4.x (ADR-0003 #5, amended); one 3.4 recording after T2 covers schema 2.

### What a run does

For each plan it runs `engine/bridge/native/record.rb` twice under `bundle exec`, with
`TZ=UTC` and `LANG=C.UTF-8`. `record.rb` loads unmodified TaskJuggler plus the shared
bridge code (`engine/bridge/request.rb`, `engine/bridge/serialize.rb`), never the
`engine/bridge/wasm/` patches or `engine/stubs/`.

1. The files under the plan's `root` that match its `files` globs (default `**/*.tjp`,
   `**/*.tji`) become the request's workspace. `GoldenFile.files` lists them, sorted; the
   parity test sends exactly these files to the worker.
2. They are copied into a private temporary workspace and `<workspace>/<entry>` is parsed
   and scheduled, as the worker does with `/workspace/<entry>`.
3. If the two runs' outputs differ, the plan fails (nondeterminism) and nothing is written.
4. Serializer cross-check: the real `tj3` CLI (`engine/tj/bin/tj3`) runs on the same
   workspace with `cross-check.tji` as a second file and writes a CSV report of every task's
   start, end, precursors and completion per active scenario. Both sides of the parity test
   share `serialize.rb`, so this is what catches serializer bugs. tj3 must agree with the
   golden on:
   - every task's start and end in every active scenario, row by row;
   - every task's precursors in every active scenario: TaskJuggler's list of the
     dependencies that end at the task (its own `depends` and the `precedes` of other tasks
     that name it), each as the other task's id and which ends it joins (`]->[`, `[->[`,
     `]->]`), compared as a sorted list with the one `cross-check-rows.mjs` derives from the golden's
     `depends` and `precedes`;
   - every `complete` the plan sets, as tj3 prints it (integer part and `%`); tj3 prints a
     computed completion for the others, which the golden leaves `null`;
   - the project's `start`, `end` and `now`, and the list of active scenarios;
   - every message up to the end of scheduling: level, id, file, line and text;
   - when neither side parses: tj3 exits non-zero and its first error has the same id,
     file and line as the golden's.

   TaskJuggler's task report has no column for gaps, the scheduling direction (its
   `scheduling` column prints ASAP for every leaf task, `TaskScenario.rb:1538`), the
   project's working time or `dailyworkinghours`. Those schema v2 fields are covered by
   parity and by the fixtures that exercise them (`syn-07`, `syn-08`, `syn-06`, `syn-13`,
   `syn-14`, the time-zone plans) only.

   `cross-check-shim.rb` is preloaded into the tj3 process. It pins `Time.now` for plans
   without a `now` line, lets `-f` still write the report after a scheduling error (tj3
   otherwise ends on the first `TjRuntimeError`), ignores `.taskjugglerrc` files, and dumps
   tj3's own project frame and messages as JSON at exit.
5. Unless `--verify` is given and every plan passed, it writes `expected/<id>.json`
   (`JSON.stringify` of the sorted object with 2-space indent and a trailing newline, no
   timestamps, so re-recording unchanged plans gives no diff) and `native-timings.json`
   (minimum of the two runs; never compared).

### `now`

A plan's own `now` line always wins. When the plan has none, the manifest's `now` is used
as `options.now`, which stands in for the system clock that TaskJuggler reads for its
default (`TjTime.new.align(3600)`). It is set when the project is created, so `${now}` and
`${today}` macros see it. `options.now` must be ISO 8601 UTC with seconds, a real date and
time, and on a whole UTC hour (`2026-01-05T09:00:00Z`); anything else is rejected as an
invalid request, by the bridge and by the recorder's manifest check, rather than rounded.
The cross-check pins `Time.now` of the `tj3` process to the same instant, so both see the
same `now`.

### Text encoding

Workspace files are UTF-8 text on both sides, and both sides use the same rule
(`MainspringBridge.normalize_text` in `engine/bridge/request.rb`, shared code):

- invalid UTF-8 byte sequences become U+FFFD, one per maximal invalid subpart. This is what
  the browser's `TextDecoder` (and Node's `Buffer#toString`) produce, so the native recorder
  sees the text the browser would. Ruby's `String#scrub` was checked against `TextDecoder`
  on 22 invalid-sequence vectors and agreed on all of them;
- exactly one leading byte-order mark (U+FEFF) is removed by the bridge;
- CRLF and CR line ends become LF inside TaskJuggler itself, on both sides.

**Decoding rule for the JS side.** The worker (T6) and the parity harness (T11) must
decode file bytes with `new TextDecoder('utf-8', { ignoreBOM: true })`, which replaces
invalid sequences with U+FFFD and keeps a leading BOM, and leave BOM removal to the bridge.
The default `TextDecoder` drops the BOM itself, so a file starting with two BOMs would then
reach the bridge with one where the native recorder had two, and the outputs would differ.

So a golden describes what the browser engine gets after decoding, not what `tj3` does with
raw invalid bytes (it stops with `UTF-8 encoding error`). The upstream Tutorial is valid
UTF-8: its `©` on line 37 is the two bytes `C2 A9`. Plain `tj3` fails on it only when the
locale is not UTF-8 (for example `LANG` unset, so Ruby reads files as US-ASCII). The
recorder sets `LANG=C.UTF-8`, passes `-EUTF-8` to Ruby, and the bridge sets
`Encoding.default_external` to UTF-8, so the locale cannot change results.

### Fields worth knowing

- `column` is always `null`: TaskJuggler 3.8.4 records line numbers only (every
  `SourceFileInfo` has column 0). `line` 0 is also emitted as `null`.
- Messages carry their scenario: the bridge turns off TaskJuggler's `hideScenario`, which
  `tj3` leaves on. Paths in `file` and in message text are workspace-relative.
- `ProjectInfo.version` and `ProjectInfo.timezone` are `null` unless the plan writes them.
- After a parse error, `project` is filled if the project header was complete, and `tasks`,
  `resources` and `bookings` are empty.
- `milestone` is scenario-specific in TaskJuggler; `TaskResult.milestone` is its value in
  the first active scenario.
- Schema 2 (`docs/phases/phase-2.md` 6.1; where TaskJuggler keeps each value is cited in
  `engine/bridge/serialize.rb`):
  - `ProjectInfo.dailyWorkingHours` is the plan's `dailyworkinghours` (default 8).
  - `ProjectInfo.workingTime` is the project scoreboard after scheduling as merged
    `[start, end)` minute pairs: global working hours minus global leaves, in the plan's
    time zone. It is empty after a parse error, because TaskJuggler builds the scoreboard
    only when it schedules.
  - Per task and scenario, `direction` is `asap` or `alap` from TaskJuggler's `forward`
    flag after scheduling, and `complete` is the plan's value or `null`.
  - `depends` and `precedes` are TaskJuggler's lists after inheritance, in its order: the
    other task's full id, `onEnd`, `gapDurationMin` (calendar minutes) and `gapLengthMin`
    (working minutes). When a scheduling error stops the run before TaskJuggler resolves a
    task's entries, the bridge looks them up the same way; an id that names no task is left
    out (TaskJuggler reports it).

### Time-zone edge cases

`tz-edge-cases.json` is a shared table with two lists. `cases` are local times at offset
changes: zone, TaskJuggler date text (`2026-03-08-02:00`), the UTC instant native TaskJuggler
gives it, and a kind (`gap`, `overlap`, `before`, `after`, `plain`). It covers New York, Los Angeles, Santiago and Sao Paulo
(west of UTC; Santiago and Sao Paulo change at local midnight), Berlin, Sydney, Lord Howe
(30-minute change) and Kathmandu (1986 change to +05:45). Native Ruby's `Time.local` (on glibc,
Ruby 3.3 and 3.4 alike) resolves them so:

- a gap time (skipped by a forward change) is read with the offset in force before the change,
  so New York `2026-03-08-02:30` is 07:30Z, shown as 03:30 EDT;
- an overlap time (repeated by a backward change) is the later instant, so New York
  `2026-11-01-01:00` is 06:00Z (EST).

`resolutions` are the largest `timingresolution` TaskJuggler accepts after `timezone`
(`Project.maxScheduleGranularity`): 60, 30 or 15 minutes as the zone's offset on 2000-01-01
ends in :00, :30, or :15/:45. It reads that offset with `Time#getlocal`, so Australia/Lord_Howe,
in summer time (+11:00) on that date, gets 60 although its standard time is +10:30.

`engine/bridge/wasm/tj_wasm_tz.rb` implements both for ruby.wasm with Intl offsets (its header
lists every zone-reading `Time` method TaskJuggler uses and what the patch does with it; `%Z`
and `Time#zone` are the one known gap). The table is checked on both sides with
`tz-edges.mjs`:

| Command | What it checks |
| --- | --- |
| `node engine/golden/tz-edges.mjs --native` | Native TaskJuggler: `tz-edge-cases.rb` parses each date with `TjTime` and reads each cap from `Project.maxScheduleGranularity` after setting the zone, in one Ruby process (developer only, like the recorder; `record-native.mjs` also runs it before recording) |
| `node engine/golden/tz-edges.mjs` | The built wasm engine in Node: one generated plan per zone and change with one milestone per case, and one plan per cap that sets the next value above it, which must fail with `too_large_timing_res` (`run-wasm.mjs` runs it after the corpus) |

The table's unit tests (`tests/golden/tz-edges.test.ts`) also check every entry against the
rules above with Node's own Intl offsets, so CI covers the table without Ruby, and the TJP value
code (`src/lib/tjp/values`, `localToEpoch` and `checkTimingResolution`) is tested against all of
it.

For a far wider check of the patch, `ruby engine/golden/tz-patch-sweep.rb [from [to [zone...]]]`
(developer only; needs zdump, no gems) loads `tj_wasm_tz.rb` into native Ruby with glibc's
offsets standing in for Intl and compares `Time.local` with native around every change of every
tzdata zone, 1970 to 2037 by default. It exits 1 on any difference it cannot explain; with Ruby
3.3.6 and tzdata 2026e the only differences are 206 local times at changes off a quarter hour
(the patch's offset cache) and 4 in the three-hour Antarctica/Rothera overlap of 1976.
`syn-21-tz-dst-edges-newyork` and `syn-22-tz-kathmandu-resolution` are the full-plan
counterparts.

## Running the goldens in the browser engine from Node

`run-wasm.mjs` boots the built engine (`npm run build:engine` first) in Node and schedules the
manifest plans with it, one long-lived engine for the whole corpus, in manifest order:

```
node engine/golden/run-wasm.mjs [--only <id>]... [--repeat <n>] [--syntax] [--tokens] [--json <file>]
npm run golden:wasm
```

It uses the worker's own runtime (`src/engine/runtime.ts`, loaded through Node's type
stripping) with a file loader in place of `fetch`, so the manifest and hash checks, the WASI file
system, the bridge and the serializer are the ones the browser runs. Each plan's request holds
exactly the golden's `files`, decoded with `TextDecoder('utf-8', { ignoreBOM: true })`, and its
`options.now`. Results are compared as canonical JSON with `revision` and `timings` left out
(spec 6.3); it prints per-plan timings next to `native-timings.json` and exits 1 on any
difference. `--repeat` keeps the fastest of n runs; `--syntax` builds the syntax docs first, which
also shows they leave no state behind. Without `--only` it then checks the time-zone edge-case
table in the same engine (see "Time-zone edge cases"). Its exports (`bootNodeEngine`, `loadCorpus`,
`planRequest`, `compareWithGolden`) are for other Node tools. The gating parity test
(`npm run test:golden`, T11) runs in Chromium instead.

`--tokens` first runs the token oracle (below) over every file of the selected plans and checks
each stream with `checkTokenStream`; the goldens must still match afterwards, which shows the
oracle leaves no state behind.

## Token oracle (phase-1 T19)

`engine/bridge/tokens.rb` (with `token_scanner.rb`) runs TaskJuggler's own `ProjectFileScanner`
over one text and returns every token and trivia item with its offsets, so that the TypeScript
port of the scanner (`src/lib/tjp/grammar/tokens.ts`) can be checked against it
(`tests/grammar/scanner-diff.test.ts`). It is test-only and Node-only (spec 6.9):
`bootNodeEngine()` returns a `NodeEngine` (`src/engine/runtime.ts`) whose `tokens(text)` calls
`TJBridge.tokens`; the worker boots with `bootEngine`, whose `Engine` type has no `tokens`, and
the worker protocol has no message for it. The bridge requires `tokens.rb` on the first call, so
booting and scheduling do not load it. Types and `checkTokenStream` are in
`src/engine/token-oracle.ts`; the header of `tokens.rb` is the full reference.

The scanner runs unmodified: a subclass only observes its matches and replaces two hooks.
Around it, the oracle scans the text the way TaskJuggler scans a workspace file (invalid UTF-8
to U+FFFD, one leading BOM reported as a `bom` item and dropped as the bridge drops it, CRLF and
CR to LF with TaskJuggler's `forceUTF8Encoding`), expands no macro and reads no environment
variable, and reads dates in UTC (restoring the time zone afterwards).

```text
{ units: "utf16", tokens: Item[], scanError: null | { id, message, line, from, to } }
Item       { kind: "token" | "whitespace" | "comment" | "bom", from, to, text }
  token    + { type, value, line, macros: MacroRef[] }
MacroRef   { kind: "macro" | "env", from, to, name, optional, args }
```

- `from`/`to` are UTF-16 offsets (JavaScript string indices) in the text as given, `to`
  exclusive. The items tile the text from 0 to `scanError.from`, or to its end.
- `text` is what the scanner read: the slice with CRLF and CR as LF, and each macro call as `_`.
- `type`, `value` and `line` are TaskJuggler's: its token type, its value (unescaped string,
  number, TIME in seconds, DATE in epoch seconds) and the line its `SourceFileInfo` reports.
- `scanError` holds scanner errors only (`runaway_token`, `no_token_match`, `junk_after_cut`,
  `time_error`, ...). Parser errors such as "Unexpected token" never appear.

| Oracle `type` | Spec 5.1 token |
| --- | --- |
| `ID_WITH_COLON` | `ScenarioPrefix` (the colon is in `text`, not in `value`) |
| `ABSOLUTE_ID`, `ID` | `AbsoluteId`, `Identifier` (or a keyword) |
| `DATE`, `TIME`, `FLOAT`, `INTEGER` | `Date`, `Time`, `Float`, `Integer` |
| `STRING` | `String`; templated when `macros` is not empty |
| `MACRO` | `MacroBody` |
| `LITERAL` | punctuation (`<=`, `>=`, `!=` or one character) |
| any token with `macros` other than `STRING` | `MacroWord` (`EnvRef` when the call's kind is `env`) |

How the scanner's modes show up, which matters when comparing with `tokens.ts`:

- **Macro calls.** TaskJuggler splices a call's expansion after its glued prefix back into the
  line and scans on. The oracle splices in the prefix and one `_`, so `t${major}`,
  `${content}${major}` and `${?x}1d` each become one `ID` whose `macros` list the calls, and
  `"${a} ${b}"` stays one `STRING` (value `_ _`). Where the spec's `MacroWord` rule differs from
  what TaskJuggler would do with a word-like expansion, the streams differ: `${a}.b` is one
  `ABSOLUTE_ID` here, and `a-${b}` is `ID`, `LITERAL`, `ID`. TaskJuggler drops an undefined
  `${?x}` together with its prefix; the oracle never does, since it cannot know which macros
  are defined.
- **Comments.** `#` and `//` comments include their line break. A one-line `/* */` runs to the
  last `*/` on its line; a multi-line comment is one item ending at the last `*/` on its closing
  line.
- **Strings.** Quoted and cut-here strings are one `STRING` each, across lines. A cut-here
  string runs from `-8<-` to `->8-` (including the blanks before `->8-`), its value has the
  first line's indentation removed, and its `line` is the line after `-8<-`.
- **Whitespace and `MACRO`.** Whitespace runs are merged into one item. A `MACRO` ends after
  the line break that follows its `]`.
- **Lines.** A token right after a multi-line comment's `*/`, with no whitespace between, gets
  the comment's first line, because TaskJuggler moves its token start only past whitespace and
  one-line comments.
